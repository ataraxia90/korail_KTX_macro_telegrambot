# Split Reservation Backlog

## 가능한 분할예매 전체 조회/예약

상태: 후순위

### 배경

현재 분할예매는 사용자가 선택한 경유역 1개를 기준으로 동작한다.
예를 들어 `수서 -> 대전`, 경유역 `평택지제`를 선택하면 다음 조건을 만족하는 열차만 분할 후보로 인정한다.

- 직통 조회: `수서 -> 대전`
- 1구간 조회: `수서 -> 평택지제`
- 2구간 조회: `평택지제 -> 대전`
- 세 조회 결과에 같은 열차번호가 모두 존재해야 함

### 확장 아이디어

사용자가 특정 경유역 1개를 고르지 않고, 해당 경로에서 가능한 모든 중간 정차역을 후보로 삼는다.
예를 들어 `수서 -> 대전`이면 `동탄`, `평택지제`, `천안아산`, `오송`을 자동 후보로 사용할 수 있다.

### 권장 방향

조회 후보는 넓히되 예약 요청은 동시에 많이 보내지 않는다.

- 가능한 경유역 전체를 route table 기반으로 산출
- 각 경유역마다 `직통`, `1구간`, `2구간` 조회 결과를 비교
- 같은 열차번호가 세 구간에 모두 존재하는 조합만 후보로 인정
- 후보를 우선순위 큐로 정렬
- 실제 예약 요청은 전역 lock으로 한 번에 하나씩만 실행
- 한 후보의 1구간/2구간은 연속 처리
- 한 구간만 성공하면 즉시 중단하고 사용자에게 강한 경고 콜백 발송

### 리스크

- 여러 경유역과 여러 열차를 동시에 예약 시도하면 매크로성 패턴으로 보일 수 있다.
- 1구간만 예약되고 2구간은 실패하는 부분 성공 케이스가 늘어날 수 있다.
- 사용자가 기대하지 않은 경유역 조합이 먼저 성공할 수 있다.

### 우선순위 제안

1. 직통 예약
2. 사용자가 직접 선택한 경유역
3. 자동 후보 중 같은 열차번호 분할 조합
4. 목적지에 너무 가까운 경유역 조합은 후순위

### 결론

`가능한 모든 분할 후보 조회`는 유용하지만, `가능한 모든 후보의 동시 예약 시도`는 피한다.
기능 방향은 `분할 후보 자동 확장 + 단일 예약 실행기`가 적절하다.
