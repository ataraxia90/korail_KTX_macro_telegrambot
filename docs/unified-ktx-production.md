# 통합 KTX 운영 배포

운영 브랜치: `codex/unified-ktx-production`

기존 Telegram 봇과 Render Web Service를 그대로 사용하고 배포 브랜치를 전환한다.
`render.yaml`의 서비스 이름은 기존 `train-reservation-bot`을 유지한다. 실제 서비스 이름과 Blueprint 연결 상태는 배포 전에 확인한다.
봇 토큰, 대화방, 서비스 URL, 웹훅 및 실제 사용 중인 Redis DB를 유지한다.

## 적용 동작

- `UNIFIED_KTX=True`: KTX/SRT 선택 없이 코레일 통합회원 로그인으로 진행한다.
- 수서·동탄·평택지제를 포함한 경로를 기존 Korail 검색·예약 처리로 전달한다.
- KTX/전체 열차 선택, 좌석 등급, 인원 및 좌석 배정 전략은 유지한다.
- 기존 SRT 조건의 반복 예약과 SRT 작업 프로세스 실행은 차단한다.
- 분할예매는 통합 운영 범위에서 제외한다. 기존 SRTrain 분할예매를 코레일로 이식하지 않는다.
- 결제는 사용자가 직접 진행하며 기존 코레일 결제 알림을 사용한다.
- `UNIFIED_KTX`를 생략하거나 `False`로 설정하면 기존 KTX/SRT 선택 흐름이 동작한다.

## 기존 서비스 전환

1. 현재 배포 커밋·브랜치와 환경변수 설정을 복구할 수 있도록 기록한다. 진행 중인 검색은 중지하고, 이미 예약된 승차권의 결제와 알림 상태를 확인한다. 진행 중인 예약 작업을 새 배포로 자동 이어받는 기능은 없다.
2. 브랜치를 GitHub에 push한 후, **기존 Render Web Service**의 배포 브랜치를 `codex/unified-ktx-production`으로 변경한다. Blueprint 관리 서비스라면 Blueprint 연결 브랜치도 확인한다.
3. 기존 비밀 환경변수 `BOTTOKEN`을 그대로 유지한다. 기존 `ALLOW_LIST`, `REDIS_URL` 및 실제 사용 중인 `REDIS_DB`도 유지한다.
4. `USERID`, `USERPW`가 코레일 통합회원 계정인지 확인한다. 기존 SRT 전용 자격증명은 통합 모드에서 사용하지 않는다.
5. 기존 서비스의 환경변수에 `UNIFIED_KTX=True`, `SEARCH_INTERVAL=1`, `FLASK_DEBUG=False`를 적용하고 배포한다. 저장소 파일 수정만으로 실제 서비스 환경변수가 변경되었다고 간주하지 않는다.

기존 Blueprint가 `srt-mvp`에 연결된 상태에서 서비스를 직접 전환할 경우 해당 Blueprint의 `autoSync`를 끈다. 예전 YAML이 서비스 설정을 되돌리지 않도록 하기 위한 조치다. 서비스 자체의 자동 배포는 유지하여 통합 브랜치의 커밋을 배포한다. 복구 시 Blueprint 자동 동기화 설정도 전환 전 기록을 따른다.

`REDIS_DB`는 URL 경로나 쿼리에 포함된 DB 번호보다 우선한다. Blueprint는 기존과 같은 1을 사용하지만, 기존 런타임이 URL에 지정된 다른 DB를 사용했다면 그 실제 번호로 맞춰야 한다. 세션·구독·예약·결제 상태가 모두 이 DB에 저장된다. DB를 초기화하거나 다른 번호로 바꾸지 않는다.

기존 SRT 세션이나 `/repeat` 조건은 자동으로 코레일 예약으로 바꾸지 않는다. 해당 사용자는 `/start`로 코레일 로그인과 예약 조건을 다시 입력한다. 같은 토큰으로 기존 버전과 통합 버전을 동시에 실행하지 않는다.

## 연결 및 검증

- 기존 서비스 URL의 `/health` 응답을 확인한다.
- 기존 토큰으로 Telegram `getMe`를 호출해 봇 이름을 확인한다.
- `getWebhookInfo`의 URL 및 오류 상태를 확인한다. 기존 서비스 URL이 같으면 웹훅을 다시 설정할 필요가 없다.
- 추후 서비스 URL을 변경할 때만 기존 토큰의 `setWebhook`을 새 URL로 변경한다. 대기 중인 업데이트 삭제는 기본 전환 절차에 포함하지 않는다.
- 기존 봇 대화방에서 `/start` → 코레일 로그인 → 수서 출발·도착 조회를 검증한다.
- 실제 예약 검증은 사용자 지정 열차로 별도 진행한다. 단위 테스트는 외부 예약·메시지 전송을 하지 않는다.

현재 코드 테스트만으로 통합 서버의 실제 로그인·좌석 조회·예약 성공을 보장할 수는 없다. 기존 서비스의 브랜치 전환·배포, 기존 웹훅 확인, 실서버 검증이 완료되어야 운영 전환을 완료한 것으로 본다.

## 롤백

문제가 있으면 통합 버전의 검색 작업을 중지한 뒤, 기존 서비스의 배포 브랜치·커밋과 환경변수를 전환 전 기록으로 복구한다. 봇 토큰·웹훅·Redis DB는 유지한다. 진행 중이던 백그라운드 검색과 결제 알림은 자동 복구되지 않으므로 예약 상태를 확인한 뒤 다시 시작한다.
